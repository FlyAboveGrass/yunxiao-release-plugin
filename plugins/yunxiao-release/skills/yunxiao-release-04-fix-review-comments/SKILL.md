# 修复云效评审评论

先阅读 [发版契约](../../references/release-contract.md)。评论文档不存在、已过期或无法证明完整时停止，不得基于不完整评论修改代码。

## 流程

1. 按评论 ID 逐条读取未解决评论及对应文件、行号和回复链。
2. 阅读实际代码和所有相关调用方，判断评论正确、过期、重复或冲突。
3. 完成全部评论的根因分析，按评论 ID 一次性列出处理方式、拟修改文件、无需修改或拒绝处理的理由；不得为了关闭评论而修改正确代码。
4. 对全部解决方式只获得一次确认。确认后完成已列出的业务代码修改，并按适用的 `AGENTS.md`、`CLAUDE.md` 使用相应项目 Skill 和验证命令；不得在执行中扩大范围。
5. 在评论文档记录分析、实际修改和验证证据，并重新同步评论，按评论 ID 识别新增、更新和已解决评论；重新同步不得覆盖已有执行记录。
6. 一次性展示最终差异、验证结果、提交信息、推送目标，以及每条评论拟发送的回复和解决操作，并获得一次总确认。
7. 确认后依次提交、推送、回复和解决已展示的评论，不再逐项确认。每个动作成功后立即写入现有 `commentsFile` 的“执行记录”：commit 记录本地 SHA，push 记录 remote、branch 和远端 SHA，回复记录评论 ID 及返回的回复 ID 或重新查询证据，解决操作记录评论 ID 与最新状态；不创建新的状态文件。提交必须遵循项目规则和 Conventional Commits，项目存在提交 Skill 时优先使用。
8. 重试前同时核对执行记录、Git 远端和 MCP 评论状态，只跳过能够由真实状态证明已成功的动作；无法验证时停止。任一动作失败时保留此前成功记录，停止后续写操作，并一次性输出已完成、失败和待执行动作。评论状态或内容发生变化时不得套用旧确认。

## 停止条件

- 评论上下文不足或无法定位代码。
- 多条评论互相冲突。
- 类型、接口契约或预期行为不明确。
- 验证失败或出现来源不明的额外改动。
